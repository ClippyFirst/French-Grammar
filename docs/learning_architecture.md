# Архітектура навчального довідника

## 1. Мета

French-Grammar має бути не каталогом Markdown-файлів, а **навчальною системою довідкового типу** для носіїв української мови, які вивчають французьку.

Архітектура повинна підтримувати три задачі:

1. **Lookup** — швидко знайти відповідь.
2. **Learning** — пройти тему від розуміння до застосування.
3. **Navigation** — побачити, що вивчати до і після теми.

Один список related links не може якісно вирішувати всі три задачі.

# 2. Канонічна модель теми

Кожна тема має мати стабільний **canonical topic ID**, незалежний від назви Markdown-файлу.

Рекомендовані поля:

| Поле | Призначення |
|---|---|
| id | стабільний ідентифікатор теми |
| slug | URL-ідентифікатор |
| title_uk | українська назва |
| title_fr | французький термін |
| description_uk | короткий опис |
| category | навчальна категорія |
| level | орієнтовна складність |
| order | порядок у категорії |
| prerequisites | необхідні попередні теми |
| related | змістово пов'язані теми |
| contrast | теми, з якими треба порівнювати |
| next | рекомендовані наступні теми |
| tags | пошукові ключі |
| register | neutral/formal/informal/spoken/written/literary/regional |
| status | DRAFT/PARTIAL/REVIEW/DONE/REFERENCE |
| contrastive_uk | рівень L1-контрасту |

## 2.1. Related ≠ prerequisite

**Prerequisite:** що треба знати, щоб зрозуміти тему.

**Related:** що змістово пов'язано з темою.

**Contrast:** з чим треба розрізняти конструкцію.

**Next:** куди логічно рухатися далі.

# 3. Навчальний граф

Теми мають утворювати орієнтований граф залежностей.

Наприклад:

noun-gender → definite-articles → article-omission

present → imparfait → passe-compose-vs-imparfait

subject-pronouns → object-pronouns → clitic-order

Граф є навігаційною моделлю, а не жорстким курсом: користувач повинен мати можливість безпосередньо перейти до потрібної теми.

# 4. Категорії та рівні

Категорія відповідає на питання «до якої системи належить явище?».

Рівень відповідає на питання «наскільки складним є матеріал для засвоєння?».

Орієнтовна шкала:

- A1 — фундамент;
- A2 — базова функціональна граматика;
- B1 — основна продуктивна система;
- B2 — складні опозиції та підрядність;
- C1 — тонкі синтаксичні, стилістичні та дискурсивні відмінності;
- C2/REFERENCE — рідкісні, літературні, історичні або вузькоспеціальні явища.

Це навігаційний орієнтир, а не офіційна сертифікація.

# 5. Архітектура контенту

Рекомендована структура:

~~~text
src/
├── content/
│   └── fr/
│       └── *.md
├── data/
│   ├── categories.mjs
│   ├── grammar-manifest.mjs
│   └── learning-paths.mjs
├── lib/
│   ├── pages.mjs
│   ├── graph.mjs
│   ├── validation.mjs
│   └── search.mjs
├── components/
│   ├── ArticleMeta.astro
│   ├── Prerequisites.astro
│   ├── RelatedTopics.astro
│   ├── ContrastTopics.astro
│   ├── NextTopics.astro
│   ├── Practice.astro
│   └── TOC.astro
└── layouts/
    └── MarkdownPage.astro
~~~

Поточний Astro + Markdown підхід можна зберегти. CMS не потрібна лише заради методології.

# 6. Manifest як джерело істини

Потрібен один machine-readable manifest, який визначає:

- які теми існують;
- які теми заплановані;
- canonical ID;
- статус;
- prerequisites;
- contrast;
- level;
- category.

Manifest не повинен дублювати текст статей.

Його призначення — контроль повноти та графу.

# 7. Валідація

CI/локальний QA має перевіряти:

### Schema
- невідомі поля;
- відсутні обов'язкові поля;
- неправильні типи.

### Graph
- невідомі topic IDs;
- биті prerequisites;
- биті related;
- цикли prerequisites;
- сироти;
- теми без категорії;
- дублікати canonical IDs.

### Coverage
- теми з master coverage map;
- статус кожної теми;
- незаплановані файли;
- заплановані, але відсутні теми;
- дублікати.

### Content
- наявність «Швидко»;
- наявність прикладів;
- українська локалізація;
- L1-блок у темах із позначеним контрастивним ризиком;
- практика там, де вона передбачена.

### Links
- внутрішні посилання;
- canonical URLs;
- related/prerequisite links.

### Build
- Astro build;
- Pagefind;
- 404;
- accessibility smoke tests.

# 8. Структура інтерфейсу статті

Поточний layout уже має хорошу основу: breadcrumbs, TOC, контент і related topics.

Цільова структура:

~~~text
Breadcrumbs
↓
Article title
French term
Description
↓
[Level] [Register] [Status]
↓
ШВИДКО
↓
Формула / основна таблиця
↓
Використання
↓
Для носія української
↓
Порівняння
↓
Типові помилки
↓

↓

↓

↓

↓

↓

~~~

Головний принцип UI:

> **спочатку відповідь, потім пояснення, потім поглиблення.**

# 9. Режими використання

## Швидкий режим

Для lookup:

- визначення;
- формула;
- 1–3 приклади;
- коротка українська примітка.

## Навчальний режим

Для системного опрацювання:

- пояснення;
- порівняння;
- помилки;
- практика;
- prerequisites;
- next topics.

## Глибокий довідковий режим

Для B2–C1+:

- варіантність;
- регістр;
- синтаксичні обмеження;
- складні винятки;
- літературні/регіональні форми;
- джерела.

# 10. Пошук

Пошук має індексувати:

- українські назви;
- французькі терміни;
- синоніми термінів;
- українські формулювання;
- приклади;
- tags;
- category.

Запит на кшталт «коли використовувати avoir» має знаходити не лише сторінку avoir, а й релевантні теми, де avoir є частиною граматичної конструкції.

Pagefind залишається придатним як базовий статичний пошук.

# 11. Контрастивна навігація

Для носія української потрібен окремий тип зв'язку:

**French construction ↔ Ukrainian construction**

Це не означає простий переклад один до одного.

Наприклад:

**passé composé ↔ українська видо-часова система**

має пояснювати різницю систем, а не встановлювати просте «passé composé = доконаний вид».

# 12. Практика як частина архітектури

Якщо практика масштабуватиметься, її варто структурувати як дані:

~~~text
practice/
  type: choice | cloze | transform | translate | error-correction
  prompt: ...
  options: ...
  answer: ...
  explanation: ...
  difficulty: ...
  target: topic-id
~~~

Це дозволить:

- повторно використовувати завдання;
- створювати mixed tests;
- робити spaced review;
- реалізовувати interleaving;
- відстежувати topic-level mastery.

На першому етапі вправи можна залишати в Markdown, але форматувати їх послідовно.

# 13. Spaced learning

Довідник має дозволяти майбутній функціонал:

- «повторити сьогодні»;
- повернення до теми;
- mixed review;
- interleaving близьких конструкцій;
- delayed practice.

Дослідження L2 learning показують користь розподіленої практики для довготривалого засвоєння, але ефект залежить від типу завдання, кількості сесій, feedback, інтервалів і характеристик учня. Тому система не повинна будуватися навколо одного універсального інтервалу.

# 14. Українська як L1 — окремий шар

Українська не повинна бути лише мовою UI.

Вона є **контрастивним шаром даних**.

Тема може мати:

~~~text
contrastive:
  l1: uk
  risk: high | medium | low
  notes: ...
~~~

Це дозволить у майбутньому:

- будувати L1-specific learning paths;
- знаходити теми з високим контрастивним навантаженням;
- окремо тестувати українські пояснення.

# 15. Дублювання та canonical IDs

Одна граматична концепція = одна canonical topic.

Якщо два файли описують одну концепцію, потрібно:

1. визначити canonical ID;
2. вибрати canonical slug;
3. об'єднати найкращий контент;
4. оновити посилання;
5. за потреби створити redirect;
6. перевірити пошук і canonical URL.

# 16. Джерело істини

| Що | Source of truth |
|---|---|
| Текст статті | Markdown |
| Схема frontmatter | content.config.ts |
| Категорії | categories.mjs |
| Повнота тем | grammar-manifest.mjs |
| Граф залежностей | manifest |
| UI | Astro components/layouts |
| Пошук | Pagefind build |
| QA | validation scripts |

Не можна зберігати один і той самий статус у трьох різних документах.

# 17. Архітектурний Definition of Done

- [ ] кожна тема має canonical ID;
- [ ] немає дубльованих canonical topics;
- [ ] manifest є джерелом істини щодо coverage;
- [ ] prerequisites відокремлено від related;
- [ ] contrast links підтримуються;
- [ ] next links підтримуються;
- [ ] рівень і register можуть бути задані;
- [ ] L1 Ukrainian layer підтримується;
- [ ] schema валідовує метадані;
- [ ] graph validation працює;
- [ ] coverage validation працює;
- [ ] link validation працює;
- [ ] build QA працює;
- [ ] стаття має стандартизований навчальний каркас;
- [ ] пошук знаходить теми за українськими та французькими формулюваннями;
- [ ] UI не вимагає читати весь матеріал для швидкого lookup.

# 18. Архітектурний принцип

**Контентна повнота → структурна повнота → навчальна ефективність → UI.**

Оптимальний шлях — еволюційна міграція:

1. стандартизувати статті;
2. стабілізувати IDs;
3. додати manifest;
4. додати prerequisites/contrast/next;
5. додати автоматичну валідацію;
6. масштабувати практику та adaptive learning.
