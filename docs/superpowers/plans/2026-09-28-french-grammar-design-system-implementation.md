# Implementation Plan — French Grammar Design System\n\n> Date: 2026-09-28\n> Source specification: docs/DESIGN-REQUIREMENTS.md\n> Execution: native implementation in the existing Astro repository\n> Constraint: preserve static Astro/Markdown/Pagefind architecture, canonical IDs, taxonomy, and stable URLs.\n\n## Goal\nTurn the current functional site into the documented editorial grammar-reference experience: stronger typography, hierarchy, spacing, responsive behavior, accessibility, restrained French editorial character, and consistent grammar-specific patterns, without replacing the architecture or rewriting content.\n\n## Scope\n\n### 1. Foundation and tokens\n- Consolidate public/styles/global.css into a small token layer for color roles, type scale, widths, spacing, radii, focus ring, and responsive behavior.\n- Establish light/dark semantic tokens rather than component-specific color hacks.\n- Establish robust base styles for Ukrainian and French text, headings, links, selection, focus, tables, code, lists, and long-form reading.\n- Remove inline presentation styles from Astro pages where the global design system already has a semantic role.\n- Preserve print styles and reduced-motion behavior.\n\n### 2. Global chrome\n- Refine Base.astro for document-level theme initialization without visible flash where practical, while keeping JavaScript optional for content.\n- Refine Header.astro: compact editorial header, accessible controls, clear navigation affordances, no emoji UI icons.\n- Refine Breadcrumbs.astro: semantic, compact, readable breadcrumb treatment.\n- Refine Footer.astro: quiet editorial ending with useful navigation and no visual competition.\n- Keep existing routes and Pagefind integration.\n\n### 3. Reference surfaces\n- Refine src/pages/index.astro: directory-first homepage with clear proposition, prominent search, and restrained category navigation.\n- Refine src/pages/fr/index.astro: complete topic directory with strong category landmarks and scan-friendly lists.\n- Refine src/pages/fr/[category]/index.astro: category reference page with clear heading/description and topic list hierarchy.\n- Refine 404.astro to match the same visual language.\n\n### 4. Article reading experience\n- Refine MarkdownPage.astro layout around a 65–78ch reading measure.\n- Keep TOC optional and useful for long articles; use a non-heavy desktop side rail and a compact mobile presentation.\n- Improve article metadata hierarchy: Ukrainian H1, French term/title, description, then content.\n- Improve anchors/scroll margins so headings remain visible below sticky chrome.\n- Preserve related-topic graph data and improve its presentation.\n\n### 5. Grammar-specific UI\n- Define stable CSS treatments for .formula, .example, .callout, .mistake, tables, and related-topic cards.\n- Ensure French examples and Ukrainian explanations are immediately distinguishable without relying on color alone.\n- Support semantic status variants for callouts and mistakes with labels/structure.\n- Make formulas responsive: stack where semantic structure permits; preserve horizontal scrolling only for genuinely tabular data.\n- Improve table accessibility and mobile behavior without changing Markdown content semantics.\n\n### 6. Interaction and accessibility\n- Replace decorative emoji controls with accessible text/SVG/CSS primitives.\n- Improve mobile navigation state, focus management, Escape behavior where appropriate, and ARIA state.\n- Ensure keyboard-visible focus, skip link, adequate touch targets, and reduced-motion support.\n- Keep all important content usable without JavaScript.\n- Improve theme toggle semantics and synchronization with system preference only if it does not create surprising behavior.\n\n### 7. Search and polish\n- Style Pagefind entry points so search feels native to the design system.\n- Ensure Pagefind remains available from homepage/header and does not inherit unreadable dark-mode defaults.\n- Add subtle, short transitions only where they clarify interaction.\n- Avoid new dependencies unless a concrete accessibility or functionality requirement cannot be met with existing HTML/CSS/JS.\n\n## Tests to add/change before production implementation\nThe repository's current tests are mostly content/QA-oriented, so UI behavior that can be deterministically verified should gain focused tests where practical.\n\n### Test cases\n1. header-controls-use-accessible-names — search, theme, and mobile navigation controls have non-empty accessible names.\n2. mobile-navigation-reflects-expanded-state — toggle changes aria-expanded and menu visibility consistently.\n3. theme-control-reflects-current-theme — theme state and control semantics remain synchronized after toggling.\n4. design-system-has-required-tokens — global stylesheet contains the required semantic token groups and no known legacy presentation leftovers.\n5. page-layouts-avoid-inline-presentation-styles — homepage/category pages do not retain the current ad-hoc inline color/spacing rules.\n6. grammar-patterns-preserve-semantic-markup — formula/table/callout/mistake patterns retain semantic elements and do not require JavaScript.\n7. Existing full content QA remains unchanged and must pass.\n\nWhere a browser-only behavior cannot be meaningfully tested by the existing Node test harness, verify it with static inspection plus the full build rather than adding a brittle pseudo-browser test.\n\n## Implementation order\n1. Add or adjust deterministic tests for the first behavior change.\n2. Run the focused test and confirm RED.\n3. Implement minimal foundation/token changes.\n4. Run focused tests and confirm GREEN.\n5. Refactor CSS while keeping tests green.\n6. Apply global chrome.\n7. Apply homepage and directory surfaces.\n8. Apply article/grammar patterns.\n9. Apply interaction/accessibility refinements.\n10. Run full QA and build.\n11. Inspect the generated diff for accidental content/schema/taxonomy changes.\n12. Commit coherent implementation stages.\n\n## Verification commands\nPrimary:\n- npm run test\n- npm run audit:canonical\n- npm run audit:site-categories\n- npm run audit:content-schema\n- npm run build\n\nAdditional design checks:\n- search for remaining inline presentation styles in page templates\n- inspect generated HTML/CSS for stable routes and semantic landmarks\n- verify print stylesheet still excludes chrome and preserves reference content\n- verify reduced-motion media query remains present\n- verify no new frontend framework/dependency was introduced\n\n## Review focus\n- Does the new layout remain a grammar reference rather than becoming a marketing landing page?\n- Are Ukrainian explanations and French examples visually distinguishable without over-decoration?\n- Does desktop gain useful structure without a heavy permanent sidebar?\n- Does mobile become a genuine single-column reading experience rather than a shrunken desktop?\n- Are tables/formulas usable at narrow widths?\n- Are dark mode and Pagefind readable?\n- Are focus states and control names visible and accessible?\n- Did any change accidentally modify content, canonical IDs, taxonomy, routes, or static generation?\n\n## Definition of done\nThe documented design requirements are represented in the actual site code; the content model and stable URLs remain intact; deterministic tests and all existing QA/build gates pass; and the final diff contains only changes serving the documented UX/design system.
